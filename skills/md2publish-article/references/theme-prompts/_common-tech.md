# 公共技术底座（所有扩展主题共用）

> 扩展主题（本目录中无「快照」标记的文件）生成 HTML 时，把本文件 + 主题文件 + 文章原文一起交给生成模型。本文件是 wechat-html.md 五条铁律的生成版，任何主题的视觉规范与本文件冲突时，**以本文件为准**。

你是一位顶级网页设计师，精通微信公众号编辑器的兼容性限制。请按主题文件的视觉规范，把文章转换为可直接粘贴进微信公众号编辑器的 HTML。以下技术要求不可违反：

## 结构

- 输出 HTML 片段：第一行是 `<!-- md2publish {"title":"...","author":"","digest":"≤128字符摘要","source":"<源文件名>"} -->` 元数据注释，然后是一个主 `<div>` 包裹全部内容。不输出 `<!DOCTYPE>`/`<html>`/`<head>`/`<body>`
- 全局样式（背景色、padding、letter-spacing）全部写在主 `<div>` 上
- **定宽加在内容上，不加在主 `<div>` 上**。公众号在电脑端是定宽渲染的，正文不限宽会铺满整屏、长行难读；但**背景必须铺满整个画面**，所以背景色和宽度约束不能挂在同一个元素上——挂一起的话背景会跟着被夹成 800px 宽的一条，两边露出白边。分工是：
  - 主 `<div>`：背景色、padding、letter-spacing，**不写 max-width**（它负责铺满）
  - 定宽落在内容块上，每个都写 `max-width: 800px; margin-left: auto; margin-right: auto; box-sizing: border-box`：卡片式主题落在每张卡（`<section>`）；无卡片主题落在每个顶层块级元素（`<p>`、标题、`<pre>`、`<table>`、引用块）
  - 加 `margin-left/right: auto` 而不是简写 `margin: 0 auto`——简写会把主题定的上下间距一起清掉，章节间距就没了
  - `box-sizing: border-box` 不能省：不写的话卡片自己的 padding 会加在 800px 之外，各主题实际外宽随 padding 浮动
- 纯内联样式：禁止 `<style>` 标签、class、外部样式表、CDN 字体；字体族只用系统字体栈
- 禁止 `<script>`/`<iframe>`/表单元素/`position: fixed|absolute`/CSS 动画/内联 SVG

## 文本

- 每个 `<p>` 显式写 `color` 和 `text-align: left`；标题、`<section>`、`<pre>` 等块级元素同样显式写 `text-align`（主题要求居中的元素写 `center`）
- 禁止 `text-align: justify`
- 含长英文 token 的段落加 `overflow-wrap: break-word`
- 字号用 px；图片 `max-width: 100%`

## 代码块

- 内容先做 HTML 实体转义（`<`→`&lt;` 等），再换行→`<br>`、行首及连续空格→`&nbsp;`；`<pre>` 内绝不允许出现裸换行符
- `<code>` 写 `display: block; white-space: normal`；`<pre>` 写 `overflow-x: auto`
- 代码末尾无尾随 `<br>`

## 行内 code（技术文里密度最高的元素，装饰必须克制）

一篇技术文的行内 `code` 动辄一两百处（实测样本 193 处）。它和代码块不同：**它嵌在正文行里，会跟着正文断行**。

- **断行本身避免不了**：实测 193 处行内 code 在 375px 下有 46 处跨行，换什么装饰这个数字都不变（几何决定的）。能控制的是**裂开时有多难看**——实心深底会裂成两个突兀的色块，淡底或纯文字色裂开后几乎看不出来
- 所以：**不要用实心深底 + padding**，用淡底 + 小 padding、或只改文字色。别指望某种装饰能消除断行
- 主题若指定了较重的行内 code 装饰，按上述原则**降级执行**，并在交付说明里告诉用户改了哪一条
- 行内 code 不承担强调色的主要落点。它出现频率太高，把强调色派给它会让整页布满同色斑点，压过真正需要强调的内容

## 列表

- 禁用原生 `<ul>/<ol>/<li>`，用悬挂缩进 `<p>` 模拟：`padding-left: 1.5em; text-indent: -1.5em`，无序前缀 `•&nbsp;&nbsp;`（或主题指定符号），有序前缀 `1.&nbsp;&nbsp;`

## 输出压紧

- 块级标签之间最多一个换行符，绝无连续空行
- 不用空 `<p>`、`<p><br></p>` 或 `&nbsp;` 段落做垂直间距，间距全靠 margin
- `<br>` 只允许出现在代码块内
- 完整转换全文，不截断、不省略、不用"..."占位；Markdown 的 `**`/反引号等标记不得残留

## 标题（H1 不进正文）与开篇

- 文章标题（frontmatter 的 `title`，没有则正文首个 `#` H1）写进第一行元数据注释的 `title` 字段，**正文 HTML 里不渲染它**。公众号编辑器会在正文上方单独显示标题，正文再来一遍就是同一句话连出现两次
- `##`/`###` 的层级照原样映射到主题的 h2/h3 规范，**不要因为去掉 H1 就把层级整体上提**
- 主题文件里若有 h1 样式规范，在这条规则下是死条款，忽略即可，不要为了用上它而把某个 h2 提升成 h1

**没有 H1 之后，开篇要自己站住。**原文的 H1 原本承担了"压场"的作用，去掉它，正文会直接顶到第一个 h2 或第一段，视觉上像从半截开始。按这个顺序处理：

1. **首个 `##` 之前有导语段**（最常见）：这段是全文的开场，给它比普通段落更重的处理——主题的引言/摘要样式优先；主题没定义就用「略大字号 + 主文字色 + 与下方拉开间距」，不要额外发明装饰
2. **卡片式主题**（每章一张卡）：导语段单独成一张卡，或并入第一张卡的顶部，**不要让它悬在所有卡片之外**——那是本规则最容易产生的破绽
3. **正文直接以 `##` 开头、没有导语**：把首个 h2 的上间距归零（它已经在页面顶部，主题给的 margin-top 是为章节之间准备的），避免顶部出现一大块空白

## 分隔线 `---` 的语义降级

`---` 在原文里表达的是**章节分组**，不是装饰。卡片式主题里它常被直接丢弃，原文的分组语义就丢了。按主题结构选一种，不要静默扔掉：

- **卡片式主题**：`---` 落在两张卡之间时，加大这两张卡的间距（比常规卡间距大一档）来表达"这里是一个更大的断点"
- **非卡片主题**：渲染成主题的分隔样式
- **`---` 紧邻一个自带下划线/边框的 h2**：此时画线会出现双横线，丢弃 `---`，由 h2 的装饰承担断点语义

## 主题没写语法高亮时的兜底

代码块常占技术文一半面积，只给底色字色等于要求生成一块纯色砖（`docs/theme-design-lessons.md` 案例一）。主题文件若没有语法高亮规范，**不要自由发挥配色**——那会导致同一个主题每次生成的代码块长相都不同。按这个兜底来：

- 从主题调色板里取色：注释用次级灰、字符串/值用副强调色、关键字用主强调色，其余保持默认字色
- 一行上色不超过 3 类，标点和普通标识符不上色
- 暗色主题上色前先估对比度，低于 4.5:1 的色不要用作代码文字色
- 在交付说明里注明"本主题未定义语法高亮，已按底座兜底规则取色"，提示用户该主题需要补规范

## 语义映射

- `>` 引用块 → 主题的引用样式；表格 → 内联样式真 `<table>`（`table-layout: fixed`，单元格 `word-break: break-word`）；`---` 分隔线 → 主题的分隔样式或卡片间距（二选一，不要既有卡片又有孤立横线）

## 字距复位

- 主容器若设了 `letter-spacing`，所有 `<pre>`、块级和行内 `<code>` 上必须显式 `letter-spacing: 0` 复位——全局字距会撑开等宽字符，代码列对不齐

## 生成方式：用现成的机械层脚本，你只做判断层

**不要手敲 HTML，也不要重写转换脚本**——机械层已经有了：

```bash
python3 skills/md2publish-article/scripts/md2html.py <article.md> <theme.json> -o <out.html>
```

它包办所有与主题无关的部分：实体转义 → 行首/连续空格转 `&nbsp;` → 换行转 `<br>` → 包装饰 `<span>`（顺序固定，装饰 span 绝不跨 `<br>`）、段落/列表/表格/引用的结构包裹、语法高亮的 tokenize 与渲染、定宽加在内容块而非主容器、H1 不进正文、跑完自动做代码块逐字节反解核对。

**你要做的是判断层**，就是写那份 `theme.json`：

- 把主题文件的散文规范翻译成内联样式串（`container` / `card` / `h2` / `pre` / `inline_code` …字段说明见脚本头部注释）
- `highlight` 里给语法高亮的 token 取色（主题没规定就按上面的兜底规则从调色板取）
- 哪几段升格为提示卡、主题没覆盖的元素怎么按气质补齐——这些脚本判断不了

提示卡分两步，缺一步就不生效：`theme.json` 里配 `alert`（主题文件规定了提示卡才配），**并且**在文章 markdown 里给该引用块首行加 GitHub Alert 标记：

```markdown
> [!NOTE]
> 这段读者跳过会踩坑。
```

`NOTE` / `WARNING` / `TIP` / `IMPORTANT` / `CAUTION` 五种都认，主题只配了 note/warning 时后三种按语气归并。**没配 `alert` 的主题，标记会被剥掉、照普通引用块渲染**——所以标记加错了不会漏字，但也不会有卡。升格的判据看主题文件自己怎么规定，一般是「读者跳过这段会踩坑」；只是补充说明的旁注不要升格，宁可一张都不做。

这样分工是因为：转义顺序、`&nbsp;` 边界这些坑对所有主题都一样，每次重写一遍就是每次都有一次写错的机会。把它固定下来，同一个主题不同次生成的结果才可复现。

脚本没覆盖到的语法（复杂嵌套、`:::module` 之类）仍然由你手工补，补完照样要过自检。

依据与案例见 `docs/theme-design-lessons.md`。
