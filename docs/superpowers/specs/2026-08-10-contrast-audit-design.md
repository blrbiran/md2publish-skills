# 设计：全库对比度审计（`contrast-themes.py`）

> 2026-08-10 立项。与 `audit-themes.py`（主题文件自洽）、`census-themes.py`（声明的色有没有落点）
> 并列的**第四套机械检查**：落下来的东西读不读得清。
>
> 本文是项目级存档（见 handoff 第零节第 4 条），计划收尾后不逐轮更新；发现**事实错误**时回来更正并留痕。

## 一、为什么要有这一层

`census-themes.py` 现在报 **0 条未销**，但那个 0 只覆盖「主题文件声明的色，在产物里有没有落点」。
对比度它一个字都查不到——本项目至今处理过的两处对比度不达标（terracotta-sun 的
`highlight.comment` 2.58:1 与 `highlight.keyword` 3.39:1）**全是人手量出来的，普查一声不吭**。

handoff 1.5 末尾挂着五条「待核的线索」，并明写**「没有做过全库对比度审计」**。
本轮实测证实：那五条是严重低估。

**实测基数：26 个主题里 18 个有不达标组合，合计 113 种。**

> ⚠️ **113 是下限，不是本文规则的最终数字，实现时不要拿它当验收值。**
> 这个数出自立项探针，而探针的装饰判据用的是「文本里没有字母/数字/CJK」——**正是
> §4.3 规则 2 否掉的那条**。实测有 **43 种组合处在 3.0–4.5 之间、被字符类规则判成装饰而放过**；
> 按本文的正确规则（装饰 = 由那八个注入字段产生），其中凡不是注入字段产生的都会变成实文字、
> 按 4.5 判，**成为新的基线条目**。样本里 cyber-neon 与 scarlet-tech 的 `"`（`em` 里的内容引号，
> 不是注入装饰）属于这一类；`•`/`◆` 多半来自 `list_prefix_html`、会留在装饰档。
>
> **真实基数在 113 到 156 之间，要等实现出注入字段匹配器、首跑一次才能定。**
> 首跑的输出就是基线首版；本文各处的 113 只用来说明量级。

| 对比度 | 组合数 | 例 |
|---|---:|---|
| < 2.0 | 7 | celadon-scroll 的 h2 两侧饰线 `#d8cfb8`/`#fbf7ec` = **1.45** |
| 2.0 – 3.0 | 39 | morandi-fog 引用块正文 **2.71**；candy-pop 粉底上整套（h2/表头/strong）**2.89** |
| 3.0 – 4.0 | 45 | autumn-warm 的 strong `#c06b4d` **3.54**（159 处文字）；terracotta-sun strong **3.39** |
| ≥ 4.0 但未达标 | 22 | mint-breeze **4.45**、morandi-fog **4.41** |

每主题不达标组合数（从多到少）：candy-pop 16、aurora-flow 14、washi-spring 13、
autumn-warm 12、morandi-fog 9、spring-fresh 9、arena-charge 7、lavender-dusk 6、
mint-breeze 5、terracotta-sun 5、celadon-scroll 3、botanic-press 3、retro-phosphor 3、
gilded-ink 3、blueprint-grid 2、ocean-calm 1、ink-wash 1、scarlet-tech 1。
其余 8 个主题 0 条（名单以脚本输出为准，本文不复制一份会漂的清单）。

**这 113 条与 census 的 43 条性质完全不同。**那 43 条里大半靠改标签、改描述、写注记就能销，
产物逐字节不变；**这 113 条几乎每一条都要动配色、都会改产物、都含审美判断**，而且
candy-pop / washi-spring / morandi-fog 是整套配色系统性偏浅，不是一两个色的事。
把它当成「再来一次 43 条」会低估一个量级——**这正是本文选择「冻基线」而不是「处置到 0」的理由**。

## 二、用户已裁决的四件事

立项对话里逐条拍板，实现时不要重新发明：

1. **形态是常驻护栏**，不是一次性报告——以后每次改主题都要能挡住对比度回归
2. **装饰符号按图形 3:1 判**，不按文字 4.5，也不是完全不查
3. **冻基线、只挡新增**：存量（百余条，确数见 §1 的 ⚠️）全部列出但不阻塞，
   `exit 1` 只在出现基线里没有的新组合时
4. **架构走独立的第四套**，不并进 `census-themes.py`

第 4 条的理由要记住：census 现在那个「0 条未销 + 8 条已豁免」是六个批次挣来的、
含义明确的数字。混进上百条性质不同且刻意不阻塞的发现，那个数字立刻变得没法读。
而且 census 三层都建立在「theme.json 声明了什么」上，对比度审计根本不看 theme.json 的声明
——硬并进去是两个系统共用一个壳。

## 三、数据源：数产物，不推 theme.json

**唯一输入是产物 HTML**（仓库外 `~/code/skills/writing/wechat_test/litellm-multi-provider-gateway/out/`），
theme.json 只用来认「哪些节点是主题注入的装饰」（§4 规则 2）。

**⚠️ 文件集合必须来自 `test-md2html.sh` 的 `PAIRS` 表那套权威配对，不许 `glob("*.html")`。**
`out/` 里混着中间产物：`13-cyber-neon-v7-grid.html` 不在 `PAIRS` 里，按文件名循环就会把它
算成第 27 个主题。立项探针踩过这一脚——最初报的 114 条 / 19 个主题里有 1 条来自 v7-grid，
按权威配对重算才是 **113 条 / 18 个主题**。handoff §4 已经用黑体写过「别按文件名循环」。

从 theme.json 推「一个色落在什么底上」做不到：`strong` 的色落在卡片底上是一个数，
落在引用块底上是另一个数，落在表头底上又是一个数——theme.json 里没有任何字段说得清
strong 会出现在哪几种底上。**handoff 1.5 那五条已知线索恰好都是「卡片底上的」，
是因为人只量了最显眼的那一种组合。**

这也接上项目主线：census 回答「声明的色有没有落点」，contrast 回答「落下来的读不读得清」，
两层都靠数产物，合起来才是一张网（handoff 第三节第 6 条：**改完必须去数产物**）。

## 四、判定规则

### 4.1 有效前景 / 有效底怎么算

从根 `<div>` 往下走祖先链，每层维护 `(color, 有效底, font-size, font-weight)`：

- `color` / `font-size` / `font-weight` **继承**，子元素声明则覆盖；根默认 `16px` / `400`
- **有效底 = 最近一个声明了底的祖先**：`background-color` 打底，再把 `background-image`
  的色标按 alpha 依次合成上去（`c = α·上层 + (1−α)·下层`）
- **祖先链上没有任何底色声明 → FAIL，不许默认按白算。**立项探针是默默兜白的
  （今天实测 0 处，所以从没暴露），但静默兜底一旦哪天真的发生，量出来的全是编造的数字。
  产物的最外层 `<div>` 按结构必然带 `container` 的底，真出现无底节点说明结构假设已经不成立，
  该停下来看，不该继续算

**走完必须回到栈底，否则 FAIL 并指出是哪份产物。**栈错位会静默污染全部测量，
是这套脚本最危险的失效模式。已实测：当前 28 份产物栈全部干净闭合（0/28 残留）。

### 4.2 渐变底：沿渐变采样取最差，不要只看端点

产物里的 `background-image` 有两类，**必须用同一套通用规则处理，不许开特例**：

| 出处 | 声明 | 性质 |
|---|---|---|
| aurora-flow 的 h2 与卡顶条 | `linear-gradient(135deg, #6a5cff, #38c6d9)` | 不透明渐变，真正换底 |
| autumn-warm / ocean-calm / spring-fresh / blueprint-grid | `linear-gradient(rgba(...,0.02~0.08) 1px, transparent 1px)` 等 | 纹理，alpha 极小 |
| morandi-fog | `linear-gradient(transparent 62%, rgba(176,142,138,0.35) 62%)` | 下划线高亮，**文字下半截真的压在色带上** |

通用 alpha 合成把三类一起处理干净：纹理合成完几乎不变色，结论自然不受影响，
**不需要定「alpha 多小算可忽略」的阈值**。

**取最差值的算法是沿渐变按步长采样（建议 1% 一步），不是只看两端。**理由：

- 相对亮度 `L` 是各通道 `f(v)` 的加权和，`f` 在 sRGB 上是凸增函数；渐变对参数 `t`
  逐通道线性插值，所以 **`L(t)` 对 `t` 是凸的**。凸函数最大值在端点，**最小值可能在内部**。
- 因此：前景比整条渐变都亮时，最差值在 `L` 最大处 → 端点（凸性保证）；
  但前景比整条渐变都暗时，最差值在 `L` 最小处 → **可能落在渐变内部**。
- 还有第三种：**前景亮度夹在两端之间时，由连续性（介值定理）渐变中途必有一点与前景等亮，
  最差对比度就是 1.0。**

三种情况分类讨论容易写错，采样一次全覆盖。变异测试要把「只取端点」这个错误实现证死。

> ⚠️ 立项探针（一次性、已弃）在这里撞对过：它对渐变只抓裸 hex 色标，而纹理与
> morandi-fog 那三条渐变里全是 rgba、没有裸 hex，于是退回了 `background-color`，
> 结果恰好是对的。**那是撞对的不是判对的**——不要照抄探针。

### 4.3 四条判定规则

1. **大文本豁免**：`≥24px`，或 `≥18.66px 且 font-weight ≥ 700` → 阈值 3.0；否则 4.5（WCAG 2.1 原文）
2. **装饰符号 → 阈值 3.0**。判据是**该节点由 theme.json 的注入字段产生**：
   `h2_prefix_html` / `h2_suffix_html` / `h3_prefix_html` / `list_prefix_html` /
   `list_prefix_cycle` / `list_prefix_ol_html` / `blockquote_prefix_html` / `footer_html`。

   **判据不是字符类。**立项探针用的是「文本里没有字母/数字/CJK 就算装饰」，**那条是错的**：
   代码块里的 `{`、`|---|`、`---` 全是纯符号，会被误放宽到 3:1，而代码里的符号是要读的。
   按注入来源判是机械事实、可逐条核——正是 lessons 从 `REF_EXCLUDE` 那次学到的教训
   （**按挂载来源判，不按词表/字符类判**）。

   实现上按「span 的 `style` 属性精确等于该字段内联样式串」匹配；字段里没有 `style` 的
   （如某些 `list_prefix_ol_html`）退回按字段字面文本匹配。这两条路都要有测试钉住。
3. **同色块跳过**：节点自带 `background-color` 且前景色等于它 → 是色块不是字。
   活例：bauhaus-pop 的 h2 前缀 `<span style="background-color: #f0a500; color: #f0a500;">■</span>`
   ——字符与自己的底同色，**成像的是那个橙色块本身，字符本来就该看不见**；
   朴素的文字对比度检查会把它报成全库最严重的一条（1.00）。

   **这条规则只对规则 2 认定的注入装饰生效。**否则主题真把正文写成和底同色（真缺陷）
   也会被静默吃掉。
4. **代码面进网**。terracotta-sun 的 `comment` 2.58 与 `keyword` 3.39 本项目已当真缺陷修过，
   先例已定。**这与 census 的 `INVERT` 剔除代码面不矛盾**：那里剔是因为落点计数被语料体裁
   污染（行内 code 在三个互不相干的主题里各贡献恰好 193 处，是语料常数）；这里代码文字是
   人要读的，对比度不因它是代码就可以低。

## 五、基线契约

- **基线键**：`主题 ⇥ 元素标签 ⇥ 前景 ⇥ 底 ⇥ 字号 ⇥ 字重 ⇥ 装饰|文字`。
  **不含出现次数、不含样本文字**——次数随文章长短变，进了键就等于换一篇文章基线全废。
  实测比值单独存一列**只作参考、不参与比对**（避免浮点尾数抖动误报）。

  **元素标签必须在键里。**它由结构决定、不随文章长短变，所以不破坏语料免疫；
  去掉它会让 `th` 与 `strong` 这种同色同字号的组合塌成一行——修好其中一个，
  基线行还在，改进就是不可见的。实测两种口径差 1 条（含标签 113、不含 112）。
- **`exit 1` 只在出现基线里没有的新组合时。**存量全部列出但不阻塞。
- 修好一条 → 从基线删一行。**基线只许减、不许增**（与 handoff 第三节第 6 条同一条纪律）。

  **这条纪律脚本管不了**：往 `.tsv` 里追加一行就能让一条新发现消声，脚本照样 exit 0。
  census 那边由 handoff 里的期望数字锚着；这边**只能靠人读 `.tsv` 的 diff**。
  所以基线文件必须进仓库、必须人可读——它的唯一护栏是 review，不是代码。
- **stale 基线行**（基线里有、产物里没有了）：列出来并提示 `--prune`，**但不 fail**。
  换一篇语料会一次产生大量 stale，fail 会让没人敢换语料。
- 判定「可以永远这样」的走 `<!-- contrast-ok: <前景> <底> <一句话理由> -->` 写进主题 `.md`，
  与 `census-ok` / `audit-ok` 三套前缀**各认各的、互不干扰**。

  **基线行与豁免注记语义不同，不许混。**基线行的含义是「已知、未处置、还没排到」；
  注记的含义是「判定为可以永远这样」。混在一起会重演 mint-breeze 那次
  「用假理由灭真发现」（handoff 第六节 1 的 ⚠️ 块）。

## 六、组件

都放在 `skills/md2publish-article/scripts/`：

| 文件 | 职责 |
|---|---|
| `contrast_lib.py` | 走祖先链、算有效前景/有效底、alpha 合成、渐变采样、WCAG 对比度 |
| `contrast-themes.py` | 判定 + 与基线比对 + 报告；`--detail <主题>` 单主题详表；`--prune` 清 stale |
| `references/contrast-baseline.tsv` | 存量快照（首跑生成），人可读、diff 友好，进仓库 |
| `test-contrast-themes.sh` | 变异测试 |
| `test-contrast-lib.py` | `contrast_lib.py` 原语单测（与 `test-theme-lib.py` 同构） |

`contrast_lib.py` 与 `theme_lib.py` 分开：后者读 theme.json，前者读产物 DOM，输入与职责都不重叠。

单主题详表的开关叫 `--detail` 而**不叫 `--counts`**：`census-themes.py --counts` 的语义是
「这个色在产物里出现几次」，这里要看的是「这个组合的前景/底/字号字重/对比度」，
两者不是一回事。同名不同义比不同名更容易骗人。

## 七、边界与明确不做

- **语料缺失整体 SKIP 并把退出码标红**——与 handoff 第三节第 3、6 条同纪律，
  静默跳过等于没有护栏
- **不做边框色 / `hr` / `box-shadow` 的对比度**：不是文字节点，第一版 YAGNI
- **不做微信浅色模式模拟**：handoff §6.2 那条「浅色模式把背景映射为白」是渲染环境问题，
  已由用户认领真机验证。护栏替它下结论只会得到没有事实基础的数字
- **不给修复建议色**：选色是审美判断，脚本报事实就够了

## 八、测试纪律

照 `test-census-themes.sh` 的范式，**每条错误实现单独证死**。至少这些必须红：

| 错误实现 | 要被哪种 fixture 抓住 |
|---|---|
| 忘了 alpha 合成 | morandi-fog 形态的 0.35 高亮带 |
| 渐变只取端点 | 前景亮度夹在两端之间的样本（正确答案 1.0）+ 前景比整条渐变都暗、最小值在内部的样本 |
| 装饰改用字符类判 | 代码块里的 `\|---\|` / `{`（必须仍按 4.5 判） |
| 同色块规则放宽到非装饰节点 | 正文色等于卡片底的样本（必须仍报） |
| 大文本阈值写成 `>18px` 或 `>18.66px` | **要两条**：`18.66px/700`（必须判为大文本，钉住边界含等号）+ `18.2px/700`（必须**不**判为大文本）。只放一条 18.66px 抓不住 `>18px`——那个错误实现下 18.66 照样算大文本，mutant 活着 |
| 栈不闭合时继续算 | 故意残缺的 HTML |
| 基线比对把比值算进键 | 比值尾数变化但组合不变的样本（不许报新增） |
| 装饰按 `style` 匹配失败时不退回字面文本 | 没有 `style` 的注入字段 |
| 用 `glob("*.html")` 取文件而不是走权威配对表 | 目录里放一份不在配对表里的多余 HTML（形态照 `13-cyber-neon-v7-grid`），条数不许变 |
| 无底色祖先时默默按白算 | 一份最外层不带 `background-color` 的 HTML（必须 FAIL，不许出数字） |
| 基线键漏掉元素标签 | 同主题、同色、同字号字重但分属 `th` 与 `strong` 的两条（必须是两行，不许塌成一行） |

外加一条 `real-library`：对真实库跑出的条数必须**与基线文件里的行数一致**。
**不要在测试里写死数字**——首版基数要等实现出注入字段匹配器后首跑才能定（见 §1 的 ⚠️），
写死一个来自探针的数会让这条测试变成「测探针」而不是「测实现」。

## 九、已知局限（写下来，免得下一轮当成完工）

1. **只覆盖当前这一篇语料渲染出来的组合。**某个主题的某条规范在这篇文章里没有触发
   （比如语料里一个有序列表都没有），它的对比度就没被量过。这与 census 的语料盲区同源。
2. **不判观感。**4.5 只是可读性下限，过线不等于好看，也不等于分层清楚。
   retro-phosphor 的三级绿就是明知 4.10 也不能改（改了就丢掉分层，见 handoff §6.2）。
3. **不判微信实际渲染。**产物是可粘贴 HTML，微信编辑器可能改写样式；本脚本量的是
   HTML 自身声明的值。
4. **`contrast-ok` 注记同样会「从写下来那一刻就是错的」。**写注记前必须先把该组合的
   前景/底/字号字重都核一遍，不要凭印象——mint-breeze 那条假理由注记就是这么来的。
