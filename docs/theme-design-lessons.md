# 主题设计经验教训

> 记录扩展主题在真实生成中翻车的模式、修法和由此形成的规则。新增或修改主题前先读本文。

## 案例一：editor-slate 黑白化（2026-08 实测）

### 现象

用户拿到成品后的原话："配色太单调了，跟 GitHub 给人的感觉不太像，只看到 # 号是蓝色的。"色值普查证实：全文 9 种颜色里强调蓝 `#0969da` 只出现 7 次，且全部落在 h3 的 `#` 前缀上；13 个代码块内部只有底色 + 字色 2 种颜色。整篇实际观感是黑白灰，与主题宣称的"GitHub 视觉语言"严重不符。

### 根因（两层）

**第一层：调色板不等于落点。** 主题文件的「色彩系统」列了强调蓝，但组件规范里蓝色的具体落点只有 h3 前缀、em 和链接——后两者在中文文章里几乎不出现（中文很少用斜体强调，公众号正文没有超链接文化）。生成模型只执行具体指令，不会自己把调色板里的颜色"找地方用掉"。**声明了但没有高频落点的颜色，等于没有。**

**第二层：大面积元素没有内部规范。** 技术文里代码块常占页面一半面积。主题只给了代码块的底色和字色，等于要求生成一块纯色深砖——而 GitHub 的辨识度恰恰来自代码块内的语法高亮（正文越素，彩色代码越跳；只抄"素"的那一半，就只剩素）。

### 修法

1. 新增「语法高亮（必做）」节：GitHub Dark 官方 6 色 token 映射表 + 按语言（YAML/JSON/Bash/Python）的落点建议 + 分寸规则（标点和普通标识符保持默认色，一行上色不超过 3 类，防矫枉过正成彩虹）
2. 提示卡从「可选」改为「遇到就用」，并写明判断标准（"读者跳过会踩坑"）和数量上限（2–4 张）
3. 表格补斑马纹
4. 修复后复测：代码块内 6 种 token 色共 213 处，用户确认观感达标

### 后续（2026-08 全主题实测）

editor-slate 那次修复**只治了一半**。补语法高亮让代码块变彩了，但正文里强调蓝的落点仍然只有 h3 前缀、em、链接——em 和链接在中文技术文里近乎为零。实测产物里正文强调蓝仅 **11 处**，整篇观感达标完全是靠 13 个高亮代码块撑住的。换一篇代码占比低的文章，同样的翻车会再来一次。

真正的修法是给 strong 上强调色（已改）。**这条记在这里是因为它揭示了一个更普遍的错误：修复症状所在的元素（代码块），不等于修复根因（正文落点不足）。**

## 案例二：宽度回归（2026-08 实测）

### 现象

用户在电脑浏览器里对比新旧产物，发现新产物铺满整屏，而早期的 `article.html` / `article-v2.html` 是定宽的——后者更接近公众号在电脑端的真实渲染。

### 根因

CLI 的 V4.0 提示词里「卡片式布局」有一条 `最大宽度: max-width: 800px`。主题被改写成扩展主题格式时**这条被丢掉了**，而 `_common-tech.md` 从来没有接住它。结果：走 CLI 快照路径的产物有定宽，走扩展主题路径的 27 个主题**全部没有**。机械核查确认 27 个主题文件里没有一个提到 `max-width`。

### 教训

**把一份规范改写成另一种格式时，丢失条款是静默的。**改写关注的是"新格式该长什么样"，没有人逐条检查"旧规范里哪些条款没被接住"。而这类丢失不会报错，只会在几个月后由用户在浏览器里发现。

改写规范时的机械做法：把原规范里所有**可验证的技术条款**（数值、属性名）抽成清单，逐条确认在新规范里有对应落点，没有的要么保留要么显式记录为"故意删除"。

### 顺带暴露的检测缺口

这个回归存在了整整一个架构周期，**自检脚本一次都没报过警**——因为脚本只检查"有没有做错"，不检查"有没有漏做"。同批还发现自检脚本对属性截断（`style` 里引号不配对导致整段样式失效）也完全无感。两项均已补进 `wechat-html.md` 的脚本。

## 规则（新主题必须满足）

1. **每个强调色至少有一个高频落点。** 高频元素：h2/h3、strong、列表前缀、引用块边框、表头——每篇文章必然多次出现。低频元素：em、链接、脚注——中文公众号文章里可能整篇为零。强调色只落在低频元素上的主题，产出必然黑白化。
2. **大面积元素必须有内部规范。** 技术向主题的代码块、图文向主题的图注、数据向主题的表格——凡是可能占大版面的元素，只给外壳颜色不够，要写清内部的颜色分布。
3. **调色板里不留死色。** 声明了就要在组件规范里指明落点（哪怕只是"题注、次要信息文字"）；指不出落点的颜色从调色板里删掉。
4. **分寸规则和落点规则成对出现，而且必须互相自洽。** 只写"多上色"会彩虹化，只写"克制"会黑白化。每个主题既要有颜色下限（保底落点），也要有上限（频率/面积预算）。**成对还不够——两条要能同时成立。**2026-08 实测抓到两个反例：ink-wash 写"朱砂频率要低"却把朱砂派给了行内 code（193 处）；ocean-calm 写"一行不超过 2 类上色"却要求"字符串、值、键名全部上色"。字面执行必然违反自己的分寸条款，生成模型只能自行取舍，产物就不可复现了。写完一对规则后，拿本仓库这篇 2.8 万字符、13 代码块的测试文当尺子算一遍：按落点规则这个颜色会出现多少次？超没超过分寸规则给的预算？
5. **黑白是一种设计时要显式声明。** monochrome-mag 无一处彩色是定位本身，文件里写明"无一处彩色"；没写这句的主题出现黑白化就是缺陷。但**声明了无彩色不等于可以没层次**——monochrome-mag 原先只给了两级文字灰，13 个代码块照写就是一块块纯色砖。无彩色主题反而要把灰阶、字重、字号的分工写得更细，因为它没有颜色这个后备手段。
6. **落点分「文字色」和「装饰色」两类，装饰落点不算数。** cyber-neon 的副强调品红有落点（h3 的 `border-left: 3px`），机械扫描不报警，但产物里品红只出现 8 次、全是 3px 细线，在 10 万字符的文档里视觉权重接近零——用户的反馈是"这个蓝色有点单调"。**强调色必须至少有一个高频的文字色落点**（h2/h3 文字、strong、符号前缀），只有边框、细线、小色块的强调色等同于死色。
7. **行内 code 不承担强调色，且装饰必须抗断行。**它还有第二个危害：**与 strong 撞形**。cyber-neon 实测（2026-08）里行内 code 和 strong 都是青色、都不带底，用户的原话是「区分不出来哪些是行内 code，哪些是强调的文字」。两者要靠**形状分工**分开——一个变色不带底，另一个带底不变色。修法是给行内 code 一个底 + 正文色文字，青色落点从 280 降到 87，品红才有了对比空间。
   **底色要往亮里调，不是往暗里调**：第一次修给了比卡底暗一档的 `#10182a`，用户反馈仍「看不清」，量出来色块对卡底只有 **1.14:1**，等于没有块。改用比卡底亮一档的面板边线色 `#39456b`（1.65:1）才立得起边界。这和主题文件里那条「面板底必须比主容器亮一档，否则十几张卡看不出边界」是同一条规则，只是换了个尺度出现——**暗色主题上，分层靠往亮里走，往暗里走会一起糊进背景**。文字对比度不是这里的瓶颈（暗底上正文色轻松过 11:1），量错了对象就会连修两轮。
   **判据是「撞不撞形」，不是「用没用强调色」。**全库 27 个主题里有 17 个给行内 code 派了强调色文字，其中 15 个带淡底——带底它就有自己的形状，和 strong 分得开，实测观感达标。真正翻车的只有 cyber-neon 那种**无底 + 强调色文字**：与 strong 同色又同形，读者没有任何线索能分开两者。
   这一档（脚本的 **OVER**）第一版写宽了，判据只看"文字色是不是强调色"，一跑报了 15 个主题。**一个检查项报了大半个库，通常是判据下宽了，不是库烂了**——先去看那 15 个是不是真缺陷，再决定改库还是改判据。收窄成"无底才报"之后归零。（这条的镜像——判据收窄到报 0 条而缺陷仍在，比下宽更危险，因为看起来像成功——见「机械审计方法」节 `census-themes.py` 的 `REF_EXCLUDE` 教训。）
   写这一档时变异测试抓到两个真 bug：一是 `background-color:` 字符串里含 `color:`，正则不挡就永远取到底色；二是有的主题把代码块和行内 code 写在同一行（autumn-warm），在整行里搜会先撞上代码块的色值。两个都是漏报，都是**测试用例的形态不够杂**造成的——第一轮 4 个变异全是"行内 code 独占一行"，就漏掉了第二个。**新增检查项必须配变异测试，而且变异要覆盖真实文件里出现过的书写形态。**
 技术文里行内 code 密度极高（实测样本 193 处）。把强调色派给它，整页会布满同色斑点，压过真正需要强调的内容（ink-wash 的朱砂、bauhaus-pop 的黄）。更要命的是它跟着正文断行——实心深底 + padding 的装饰在 375px 窄屏下会从中间裂成两截，实测 193 处里 47 处断行。用淡底、小 padding，或只改文字色。已写入 `_common-tech.md`。

8. **同一个目标只在一处给色值。** 2026-08 全库实测里 4 个主题（morandi-fog、mint-breeze、aurora-flow、newsprint）都栽在同一个形态：「色彩系统」段说某个色的落点包含引用块文字/h3 文字，「组件规范」段又给那个元素写了另一个色值。两处都是字面规范，模型只能猜。**四个主题独立出现同一形态，说明这是写作方式的问题，不是笔误**——色彩系统段只声明「这个色是什么角色」，具体落到哪个元素、用什么值，一律只写在组件规范段。已有的冲突按「更具体的组件级值优先」裁决，但正确的解法是把重复的那句删掉。审计脚本抓不到这种：它的 DESYNC 查的是「调色板有零落点色 + 组件有未声明色」，两段都声明、值不同的形态不在其中。
9. **规定了语法高亮，就要给一组在自己代码底上够对比度的色。** 实测 4 个主题（gilded-ink、terracotta-sun、aurora-flow、velvet-stage）的调色板里没有任何一个色在它自己规定的代码块底色上达到 4.5:1。更能说明问题的是**四个执行者给出了四种不同的处置**：调深造新色、改派主题内其它色、提亮造新色、判定不可用退回默认字色。**四种处理意味着这条根本没有判据**。判据应当是：先在调色板内找达标的色；找不到就退回默认文字色（放弃该 token 的上色），**不要自己造主题文件里没有的色**——造出来的色只活在 `theme.json` 里，主题文件下次重写时它就消失了，而且审计脚本只扫主题文件，永远看不见它。真要新色，是主题文件该补。
   **走「主题文件该补」这条出口时，必须两处都写：调色板里声明角色 + 组件规范里给落点。**2026-08 给 gilded-ink 的两支代码金转正时只补了调色板，`audit-themes.py` 立刻报 `DEAD`（调色板有色、组件规范找不到落点）外加一条 `DESYNC`——规则 3 的机械形态在这里正面咬人。补完 `## 引用 / 代码 / 列表 / 表格` 段的语法高亮那一行才归零。顺带：转正是**纯文档动作**，`theme.json` 早就有这两个值，改完产物必须逐字节不变——不变才证明你只是在把既成事实写下来，变了就说明顺手改了渲染。
10. **暗色主题的分层缺陷会跨主题复发，修一个不等于修完。** cyber-neon 的行内 code 底色往暗里调（规则 7）修完之后，midnight-study 里原封不动地存在同一个缺陷：它规定行内 code 底 `#191512`，比卡底 `#2b241e` 更暗。**修完一个暗色主题的分层问题，要立刻去看另外三个**（midnight-study / velvet-stage / retro-phosphor）——它们是同一批设计出来的，缺陷也是同一批。

11. **对比度铁律优先于主题的美学分寸。** 2026-08 实测两个主题的定稿产物违反 4.5:1：morandi-fog 的 h3 标题文字在卡片上只有 **2.41:1**（标题不可读），mint-breeze 的引用块文字 **3.87:1**，且它的两个候选色（`#7fa091` 2.42、`#5a7d6d` 3.87）**都不合格**——这不是二选一。两处的根因都是把主题的气质词当成了降对比度的许可：「莫兰迪的明度微差」「次级灰绿要够次级」。**低饱和、次级、克制都是手段，不是掉到阅读门槛以下的理由。**修法是把色调深到达标，而不是把元素改用正文色——后者会让辅强调只剩边框（撞规则 6）或让引用块失去层次。定完值要在**调色板行下面写明这个明度是被对比度钉住的、不要往浅里调**，否则下一个人只看到一个没来由的深色值，很容易调回去。
12. **浅底上成立的强调色，换到深底就不成立。** aurora-flow 的极光紫 `#6a5cff` 在浅色正文里是主强调（白底 4.83:1），但它自己规定的代码块底是深紫蓝 `#282a45`，紫在那上面只有 **3.04:1**，不能当代码里的文字色。**同一个色在两种底上是两个东西**，凡是主题里存在「浅底正文 + 深底代码块」这种混合结构的，语法高亮取色必须单独按代码底重算一遍，不能沿用正文的强调色分工。
13. **祈使句不会让颜色出现在产物里。** 主题文件里写「**必须真的用上**——声明了却找不到落点的颜色等于不存在」这类话，对产物毫无作用。aurora-flow 的次级灰带着这句话，产物里 **0 处**；apple-air 上一轮被记为「已修复」，那次修复是**往主题文件里加了一条渲染不出来的规范**（eyebrow 引导语要「逐节不同」，机械层只能给全局固定串），结果审计从此闭嘴、产物一点没变。**修法只有两种：给它一个机械层给得出的落点，或者按规则 3 从调色板里删掉。**加强调语是第三种，它只会让审计安静下来。
14. **写位置性或语义性的规范前，先确认机械层有对应的挂载点。** newsprint 的「全文第一段做导语处理」在产物里 **0 处**，因为脚本原本所有段落一律走同一条规范。这类规范分两种命运：**位置可判的**（全文第一段、每章第一个 h2）该给机械层加字段（`p_first` / `h2_first`），**内容语义的**（哪个数字算「关键」、哪段该升格提示卡）机械层永远给不了，要么交给判断层要么别写。新增字段的准入线是三条同时成立：**机械可判 + 无替代表达 + 当前静默丢失**——只满足前两条（比如 blueprint-grid 的章节自增编号有 `§` 顶着）就不该加。
15. **写语法高亮 token 表前，先核对 `md2html.py` 的 tokenizer 实际能产出哪些类。** editor-slate 的 GitHub Dark 表声明了 6 种语法角色，但 `md2html.py:104-126` 的 tokenizer 只发 `comment`/`string`/`key`/`keyword`/`number` 5 个类，没有「函数名/类名」和「变量/属性/参数（如 `--flag`）」这两类。这两条不是规则 14 说的「失步」（补 `theme.json` 就行）——是「无挂载点」，和 monochrome-mag 的浅中灰同类，机械层给不了，只能按规则 14 的准入线判断加不加类（这两类都可判：函数名 `\b\w+(?=\()`、`--flag` 用正则即可）。`docs/superpowers/specs/2026-08-07-product-landing-census-design.md` 第八节曾把这两条错记成失步型（当时未核 tokenizer 源码），2026-08 核对后已更正。**语法高亮尤其容易犯这条**：写主题的人参照的是官方配色表（比如 GitHub Dark 的 6 色），不是这份仓库 tokenizer 实际实现的类集合，两者天然不同步，规则 9（不许现造色）管的是色值，这条管的是 token 类本身有没有。

### 判例：定宽居中层默认了块级元素，`display: inline-block` 会让它静默失效

arena-charge 实测：h2 写成 `display: inline-block` 的黑底白字块，而该主题**没有卡片**，于是 h2 自己承担定宽，拿到 `max-width: 800px; margin-left: auto; margin-right: auto`。**inline-block 元素的 auto 外边距计算结果是 0**——黑块贴着容器左边缘，正文却居中在 800px 栏里，宽屏下每个标题都比正文左移一截。

这是案例三（定宽加错了层）的第三个形态：前两次是「加错了元素」和「被 margin 简写覆盖」，这次是「元素的 display 类型让它整个失效」。三次的共同点——**定宽居中这一层的失效方式都是无声的，样式属性都在、值也都对**。

修法不用改脚本：把色块从 h2 挪到 `h2_text_style`（这个字段本来就是为「标题文字自带色块」设计的，bauhaus-pop 用的就是它）。h2 变回块级元素正常吃定宽，色块作为内层 `<span>` 自然收缩包裹，落在内容栏左边缘。

全库扫过，只有 arena-charge 中招（washi-spring 的 inline-block 在 `footer_html` 的内层 span 上，不承担定宽，无害）。**这条机械可判**：boxed 元素的样式串里出现 `display: inline-block` 就该报警。

### 判例：`INVERT` 有一类是标签错了，不是设计错了——修法是改描述，不是写豁免

autumn-warm / ocean-calm / spring-fresh 三个同模板主题各报一条 `INVERT`。查 `theme.json`：
标成「副强调」的深色挂在 h2/h3 文字、`strong`、行内 code、表头、语法高亮上（文字落点
317 / 333 / 317），标成「主强调」的亮色挂的是 h2 符号、h3 短线、列表前缀、引用块边框、em
（各 21）。**设计完全成立**——深色承担文字（过对比度门槛），亮色做装饰（图形 3:1 线即可，
正是规则 11 在设计阶段就生效的结果）；错的只有调色板里那两个角色标签的先后。

处置是**对调两行的角色标签**，`theme.json` 一个字不改，产物逐字节不变，`INVERT` 自动消失。
这比写豁免注记好，值得单独记一条：**豁免是承认「主强调确实没什么文字落点，但有正当理由」；
对调标签是指出「这支色根本就不是主强调」。前者让脚本闭嘴，后者修正了描述。**遇到 `INVERT`
先问哪一种，别默认写豁免——豁免会把一份错误的描述永久固化下来，而下一个照着调色板改主题
的人读到的正是那份描述。

判断方法是机械的：把两支色在 `theme.json` 里的挂载键列出来，看谁扛文字、谁扛装饰
（`census-themes.py --counts <主题名>` 的「文字」列就是这个）。**逐个主题核，别因为三个主题
长得像就假设它们一样**——这次三个确实一致，但那是核出来的结论，不是前提。

### 判例：被内容类型限定的规范，全局机械字段接不住

`list_prefix_ol_html` 上连着两条同形的 `UNMOUNTED`：botanic-press 的「物种/条目清单**可用**
褐色序号」、mint-breeze 的「**步骤类**有序列表前缀数字加浅绿圆底」。两句都不是无条件规范——
一个是许可式（「可用」），一个限定内容类型（「步骤类」）——而 `list_prefix_ol_html` 是全局
字段，配上去**每篇文章的每个有序列表**都会套上那个前缀。机械层没有任何办法判断「这个列表
是不是步骤」。

这是规则 14 的一个新形态：规则 14 问的是「机械层有没有这个挂载点」，这里挂载点是有的，
**问题出在规范自己的适用范围比字段窄**。准入线要多一句：**字段的作用域必须覆盖得住规范的
作用域**；规范限定了内容类型而字段是全局的，就不是「补个字段」能解决的，要么把限定词从规范
里去掉（那是设计决定，得由人拍），要么承认接不住并留档。

mint-breeze 还有一条独立的机械理由，顺带记：那个徽章是 `width: 20px; border-radius: 50%`
的**单位数**圆，序号到两位数会撑破——**照抄规范里的示例值时，示例通常只演示了 `1`**。

⚠️ 验收时的陷阱：本仓库的测试语料**一个有序列表都没有**，所以这两条无论配不配，产物都
逐字节不变。**「产物没变」在这里不是「验证通过」，是「根本没被执行到」**——两者在
`test-md2html.sh` 里长得一模一样。

### 判例：装饰符号要避开与汉字同形的字符

velvet-stage 用 `━`（U+2501）做 h2 前缀，配上该主题的 `letter-spacing: 4px` 和居中衬线中文，用户实测反馈「以为是中文的『一』」。中文排版里挑装饰符号，先排除所有与常用汉字同形的字符（`━ ─ 一 丨 亅 丶`），几何符号（`✦ ◆ ❦ ▍`）不会有这个问题。

### 判例：主题专属的分寸条款优先于 `_common-tech.md` 的通用兜底

terracotta-sun 实测：按通用兜底规则「字符串/值用副强调色」给语法高亮取色，橄榄绿跑到 85 处，直接违反该主题自己写的「橄榄绿频率必须低于陶橙一半、只用于 em 和 h3 前缀」。改派主题内其它色后降到 8 处。

**通用兜底是给「主题没规定」的情况准备的，不是用来覆盖主题已有的分寸条款的。**两者冲突时按更具体的那条走——这和规则 8 的裁决方向一致。注意与另一条区分：`_common-tech.md` 里的**技术约束**（转义、字距复位、对比度下限）仍然优先，那些是铁律不是兜底。

## 机械审计方法

**现在有脚本了**，不要再手工扫：

```bash
python3 skills/md2publish-article/scripts/audit-themes.py
```

它对每个主题解析「色彩系统」段，逐色在组件规范里查落点，分三档报告：`DEAD`（零落点）、`LOW`（落点全在 em/链接/脚注这些中文文章里可能整篇为零的元素）、`DECOR`（强调色只当边框细线用，没有文字色落点——规则 6）。2026-08 用它扫出 5 处真缺陷（4 个次级灰零落点 + washi-spring 主强调只当细线），修完全库归零。

### ⚠️ 这个脚本查的是「主题文件里有没有声明落点」，不是「产物里这个色出现了几次」

2026-08 全库 20 个主题实测把这个盲区打穿了。**apple-air 审计 0 条，产物里唯一强调色只出现 1 次**（10 万字符全文）。它的主题文件给蓝色声明了三个落点，脚本看见了，实测三个全部不可达：

| 声明的落点 | 为什么产物里没有 |
|---|---|
| 每个 h2 上方的 eyebrow 引导语 | 内容要「从该节主旨提炼 2–6 字、逐节不同」，`h2_prefix_html` 是全局固定串，脚本给不了逐节不同的内容 |
| em / 关键短语 | 中文技术文里 em 几乎为零（就是本文案例一说的那件事） |
| 关键数字/数据 | 要判断哪个数字算「关键」，属内容语义，脚本没有这个能力 |

三个落点里两个是**内容语义**、一个是**脚本能力之外**，但它们在主题文件里都是白纸黑字的规范，所以审计一条都不报。更值得警惕的是：apple-air 上一轮被记为「已修复」，那次修复正是**往主题文件里加了 eyebrow 条款**——加了一条渲染不出来的规范，审计从此闭嘴，产物一点没变。

**结论：审计脚本 0 条不等于主题成立。** 它能证伪（报出来的基本是真缺陷），不能证实。真正的判据是对**产物**跑色值普查：

```bash
python3 -c "
import re,collections,sys
c=collections.Counter(re.findall(r'#[0-9a-fA-F]{6}', open(sys.argv[1]).read()))
print(c.most_common(14))" <out.html>
```

拿计数对着「色彩系统」段逐色核，强调色计数接近 0 就是落点失效。**这一步现在已经固化进脚本了**：`skills/md2publish-article/scripts/census-themes.py` 把「声明落点」和「实际落点」两侧都机械化。本仓库已知的四次「规范写着但产物 0 处」（apple-air 的 eyebrow、cyber-neon 的警示 strong、newsprint 的导语、aurora-flow 的次级灰）全部发生在这一层，而审计（只看主题文件）、自检（只看铁律）、逐字节回归（只看「和上次一样」，可上次就是错的）三者都不会响——这正是这个脚本存在的理由。

### `census-themes.py`：三层九档，把「声明」和「产物」两侧钉在一起

```bash
python3 skills/md2publish-article/scripts/census-themes.py
```

它跑三层比对，分九档判定（严重度 ERROR/WARN/INFO），外加第十档 `STALE-NOTE`（豁免注记销不到任何发现时报；档名打错直接 FAIL，不许静默地什么都不销）：

| 层 | 比对什么 | 档名 |
|---|---|---|
| L1 | 主题 `.md` 色值 ↔ `theme.json` 色值 | `UNCARRIED`（声明了没兑现）、`INVENTED`（`theme.json` 现造的色，规则 9）、`INLINE-BLOCK`（承担定宽的键用了 `inline-block`，判例） |
| L3 | 散文语义条款 ↔ `theme.json` 机械字段 | `UNMOUNTED`（规范写了对应的机械字段却没配） |
| L2 | `theme.json` ↔ 产物 HTML | `ZERO`（声明了产物 0 处）、`ZERO-DUP`（已由 `UNCARRIED` 报过的 0 处，降级不消失）、`NEAR-ZERO`（产物里 ≤2 处）、`DECOR`（强调色只有装饰落点没有文字落点，规则 6）、`INVERT`（主强调文字落点少于副/辅强调或参照色，规则 11 在产物侧的回声） |

豁免注记用独立前缀 `<!-- census-ok: <档名> <键> <一句话理由> -->`，与 `audit-themes.py` 的 `audit-ok` 共存于同一批主题文件、互不相扰。`--counts <主题名>` 单独打印某个主题每个调色板色的落点分解（总/文字/面/线四栏）——把「改完必须去数产物」变成一条可以直接跑的命令，不用每次现写 `Counter(re.findall(...))`。

配套变异测试 62 条，覆盖九档 + 豁免机制（末尾 7 条钉 `NEAR-ZERO` 的 container 锚点收窄，见下文）：

```bash
bash skills/md2publish-article/scripts/test-census-themes.sh
```

**首次对真实库跑出 43 条、exit 1**（批次 1a 后 37 条、批次 1b 后 17 条、批次 2 后 10 条未销
+ 5 条已豁免，仍 exit 1；**当前数字以 handoff 第三节第 6 条为准，别信本文这个快照**）——分组、
执行顺序与逐条要点在 `docs/handoff/handoff.md` 第六节第 1 条。本文只记录判据本身与由此
得出的通用教训，**不代替那份清单**；谁改了主题文件都要重新跑一遍普查，确认发现只有
减少、没有意外新增。

**也别把「43 → 0」读成「主题库成立」。**这个脚本有一处原理性盲区（见下文「L3 看不见
纯中文写的颜色」），已知至少一条真缺陷永远不会被它报出来。这正是本项目立项时踩的那个
坑的形状——把「检查报了 0」当成「库是好的」——只不过换了一个脚本。

#### 判据可以下窄，下窄比下宽更危险

规则 7 记的是判据下宽——`audit-themes.py` 的 `OVER` 档第一版报了大半个库。**这个项目在真实工作中撞到的是它的镜像：判据被收窄到报 0 条，缺陷却还在原地，这种失败比下宽更危险，因为它看起来像成功。**下宽会被人一眼看出「报了 15 个主题，不太可能全是缺陷」，逼着你去核；下窄不会——脚本安安静静地绿了，没人会去问「是不是压根没在查」。

真实撞到的一次：复审时有人提议把 `REF_EXCLUDE`（`census-themes.py:252`，`INVERT` 参照色的排除词表，含「次级」）套到 `ZERO`/`NEAR-ZERO` 循环上，用来消掉 `NEAR-ZERO` 报出的 20 条背景色噪音。实测：`NEAR-ZERO` 确实归零了，但真实库里 aurora-flow 那条立身缺陷（次级灰零落点，本项目开工的直接起因之一）跟着一起消失——因为它的调色板标签正是「**次级**灰」，`REF_EXCLUDE` 含「次级」，这一个词表把它连带灭了口。判据窄到刚好盖住自己最初要抓的靶子，比宽到报出一堆噪音更难被发现。**这个方案已被否决，不得采纳。**

任何未来对 `NEAR-ZERO` 的收窄都必须同时满足：只作用于 `NEAR-ZERO`（`ZERO` 一律不动）、判定依据是**该色在 `theme.json` 里的挂载键**（`container`/`footer_html` 这类 `build()` 只发射一次的结构性键）而不是调色板标签、绝不能用 `REF_EXCLUDE` 这类「靠引用一组词定义自己」的表来判、candy-pop 那条挂在 `em` 上的 `NEAR-ZERO`（规则 1 的典型死色）必须继续报。

**这次收窄已于 2026-08-09（批次 1b）执行**，实测 19 条 `NEAR-ZERO` → 1 条（只剩 candy-pop 那条真死色），真实库其余输出逐字节不变。判据是：

```python
"container" in mounts and mounts <= {"container", "footer", "footer_html"}
```

**锚点是 `container`，判据不是「`build()` 只发射一次的键」——这两个说法第一版被当成同一个，是这次复审揪出来的真错。**`md2html.py:426-434` 里 `footer` 与 `footer_html` 由同一个 `if` 守着、同属文末那一个 `<p>`，**次数**跟 `container` 一样固定 ≤1；按「只发一次」推导三个键就平级，于是「唯一强调色只落在文末落款上」会被一并静默——那正是 apple-air 立项缺陷的形状。这条留给以后：

- **区分性质是面积/角色，不是次数。**`container` 是铺满整页的底，落 1 次等于全覆盖，所以「只出现 1 次」对它根本不是缺陷；文末那个 `<p>` 是个落款，落 1 次就是真的几乎没有。**只有 `container` 能提供豁免的正当性，它必须是必要条件**；`footer`/`footer_html` 进允许集合只是「不破坏已有的正当性」（retro-phosphor 把容器底色又用在文末终端行上），它们单独出现时一个都不豁免。
- **判定用子集而不是「沾一个就算」（`any(...)`）**：只要有一个挂载键在允许集合之外，这个色的落点就依赖文章内容，必须按真实计数判。
- **别往允许集合里加键。**真正危险的是「在某篇文章里可以落 0 次」的那一类（`hr`、`list_prefix_ol_html`、`td_alt`、`blockquote`、`pre`、`table`）——它们能让总数落进 ≤2 却完全依赖内容。

**第一版是怎么错的，比判据本身更值得记：文档里写的理由不是代码里实现的判据。**当时的理由写成「`build()` 只发一次的键」，实现却排除了同样只发一次的 `footer`，真正的排除依据是「加进去会让某条既有用例变红」——**按测试结果反推理由**。这类偏差不会被任何测试抓到（测试全绿），只能靠人把「我写的理由」和「我写的代码」对着读一遍。判据下窄的危险在这里又换了个形态：不是判据错，是**判据的说法**错，于是下一个人会照着错的说法去扩展它。

变异测试从 54 条加到 62 条，十种错误实现各自被对应用例证死：压根没这道门、无 `container` 锚点（第一版）、按调色板标签判、套 `REF_EXCLUDE`、`any()` 代替子集、只要锚点在就豁免（丢掉子集判定）、允许集合漏 `footer_html`、允许集合加 `hr` / `list_prefix_ol_html` / `td_alt`。两条附带纪律：

- **「只发一次」这类结构性豁免，一定要配一条「没有锚点就不豁免」的用例。**本轮补的 `l2-nearzero-footer-html-only` 就是它——第一版下它被静默，正是那个洞。
- **一条 fixture 只能多挂一个待钉的键。**第一版把 `hr` 与 `list_prefix_ol_html` 写进同一份 theme.json 去钉「集合被扩大」，结果只加其中一个时另一个仍在集合外、子集判定照样为假，用例根本不红——覆盖到不等于钉住，拆成两条才真的证死。

#### 关键词判据的两个自毁陷阱

给 `strong_alt` 这类字段配关键词判据（`census-themes.py:158-178` 的 `_negated()`）时撞到两个连在一起的坑：

- **CJK 没有词边界。** `\b` 在汉字之间永不成立——中文不靠空格分词，`\b别\b` 不会按英文的直觉工作。中文关键词要么配显式前缀黑名单（比如「别」用 `blacklist=("引",)` 排掉「区别」「分别」），要么接受会有漏报，不能指望 `\b`。
- **关键词判据如果靠引用某组否定词来定义"这不算命中"，那组词本身可能出现在被引用的例句里，让过滤器打到自己人。** `cyber-neon.md:37` 上方的原句是「不要依赖 em」——这句里的「不要」不是在否定警示语义，是在举例，但它就落在判定窗口附近。`_negated()` 用三条护栏才摁住这类假阴性：只在命中位置前后 8 字的局部窗口判、引号内的否定词不算（`「...」`/`"..."`/`` `...` `` 里视为被引用的字面串）、单字「无」只认「无+关键词」的紧邻组合。三条缺一都会在真实文件上出错。

#### 变异测试要能证明自己真的挡住了那个错误实现

`test-census-themes.sh` 的开发过程里，复审抓到过好几批「看着是覆盖、其实什么都没断言」的用例——甚至抓到一整条判断分支（`check_l2` 里 `INVERT` 的参照色分支 `for rc, rl in refs:`）可以被删掉，全部用例照样绿。当时 7 条 L2 fixture 的调色板标签全落进 `ACCENT_ROLE` 或 `REF_EXCLUDE` 两张表，`refs` 恒为空集，那条分支是死代码——把判据倍数从 3× 改成 300×，或者把整段删掉，34 条用例（当时的总数）一条不挂。

这些空洞都是靠变异测试挖出来的：人工引入一个已知错误的实现，看哪些用例挂、哪些不挂，凡是全绿的分支就单独补一条能证死它的用例。可以固化成一条通用纪律：**写完一条用例，不能只看它绿；要先说出一个"这里错了也能让这条用例照样通过"的实现，再真的去改代码验证它红。** 覆盖到不等于钉住。

#### 已知的一处盲区：L3 看不见纯中文写的颜色

`check_l3`（`census-themes.py:181-225`）只扫 `spec_lines` 挑出的、带「可机械化实体」的行——hex 色值、`style=`、`属性: 值`（`theme_lib.py:59` 的 `_ENTITY`）。一句只用中文颜色名指色、不带这些形式的散文条款，对这一层完全不可见。已知实例：`cyber-neon.md:37`「提示卡里属于警示性质的那种，标题和左边框用品红」，`13-cyber-neon-v7-edge.theme.json` 没有 `alert` 键——完全符合 `UNMOUNTED` 的定义，却因为这句没有 hex/`style=`，进不了 `spec_lines`，报的是 0。

用户已于 2026-08-07 裁定接受这个局限，不为了这一条去放宽 `_ENTITY`。量过的代价：把 `check_l3` 改成扫全部行（不经 `spec_lines` 过滤），全库只多出 2 条——这条真阳性，外加 `editor-slate.md:82` 一条假阳性（那行的「注意」「strong」是在类比优先级，不是警示 strong 的规范条款）。**放宽判据多抓一条真阳性，会同时买进一条假阳性**——这是下窄/下宽那对镜像的一个小号版本，留在这里当参照。

写这个脚本时另一个已知的坑：**一行声明两个色时，角色标签会串**（探针版把 `- 引用文字：#61638a` 下一行的 `#ecebfb` 也标成了「引用文字」）。真实主题文件里一行多色很常见，取角色时要按色值在行内的位置切分，不能整行共用一个标签。

同源盲区之一**已经堵上**：执行者为凑对比度在 `theme.json` 里现造的新色（规则 9），过去主题文件里没有、审计看不见。现在 27 份 `theme.json` 已进仓库（`skills/md2publish-article/references/theme-json/`），它们是可 diff、可 review 的一等文件，`test-md2html.sh` 的 PART B 也以仓库副本为输入。**但这引入了一个新的失步风险**：改了主题 `.md` 却没重生成 `theme.json`，缓存就是陈的——**这正是 `census-themes.py` 的 L1 层现在在管的东西**：色值在 `.md` 里改了但 `theme.json` 没跟上会报 `UNCARRIED`，`theme.json` 里有 `.md` 找不到出处的色会报 `INVENTED`。

回到 `audit-themes.py` 本身：**改这个脚本之前先跑变异测试**，它给每一档造带已知缺陷的假主题，断言脚本报什么、不报什么：

```bash
bash skills/md2publish-article/scripts/test-audit-themes.sh
```

最后一条用例会顺带对真实主题库跑一遍并要求 0 条，所以判据一旦下宽，变异用例和真实库会同时变红。用例的书写形态是照着真实库抄的（「底/文字」中文写法、纯 CSS 写法、代码块与行内 code 同写一行、散文句混在规范里），**新增形态时先去 grep 真实库里实际怎么写**——漏掉的形态就是漏报。

写脚本时踩到的坑值得记：**关键词匹配会被规范里的说明文字骗到**。第一版拿关键词在整行里搜，结果「别只挂在 em 上」这句注记让该行被判成 em 落点；把角色标签的判定改成只取冒号前的部分、把落点判定改成先解析元素名之后才干净。审计脚本对真实库跑出 0 条时，你分不清是「库真的干净」还是「脚本根本没在查」——这就是变异测试存在的理由。

以下是脚本背后的判据（脚本覆盖不到的情况仍需人工用它判断）：把「色彩系统」段的色值逐个在正文组件规范里计数，出现 ≤1 次的要人工判断——背景色出现 1 次正常（主容器只写一次），**强调色/辅助色出现 ≤1 次或落在 em/链接上即为风险**。对生成产物跑色值普查（`Counter(re.findall(r'#[0-9a-fA-F]{6}', html))`），强调色计数接近 0 说明落点失效。

- arena-charge / aurora-flow / blueprint-grid / mint-breeze：次级灰声明后零落点（死色），已补落点注记

- cyber-neon / retro-phosphor（暗色技术主题）代码块规范色数达标

## 生成方式：脚本做机械层，AI 做判断层

editor-slate v2 的生成方式被证明明显优于纯手写 HTML，固化为推荐做法（`_common-tech.md` 同步收录）：

**脚本负责机械变换**（写一次性转换脚本，不手敲 HTML）：

- HTML 实体转义 → 行首/连续空格转 `&nbsp;` → 换行转 `<br>` → 最后包高亮 `<span>`，顺序固定，从机制上杜绝"高亮标签被转义"和"转义时改坏代码"
- 语法高亮用分语言 tokenizer 产出 `(text, color)` 段再统一渲染，保证 13 个代码块规则完全一致
- 结构性包裹（段落样式、列表悬挂缩进、表格斑马纹）模板化

**AI 负责判断**（脚本做不了的）：

- 哪几段升格为提示卡、哪些保持普通引用（语义判断）
- token 上色的分寸取舍（如 `-d '{...}'` 里的 JSON 是否拆开高亮——不拆，shell 语义上它是一个字符串）
- 主题规范没覆盖到的元素（h1、分隔线、TOML）如何按主题气质补齐

**核对必做**：自检脚本 PASS 之外，把每个 `<pre>` 反解（剥 span → `<br>`→换行 → `&nbsp;`→空格 → 实体还原）与源 Markdown 逐字节 diff，证明高亮没有改坏代码。

这个分工的收益：两次实测（autumn-warm 手写版、editor-slate 脚本版）中，脚本版一次通过全部自检且 13/13 代码块逐字节保真；手写版容易在重复劳动（逐块转义）上出不一致。

## 案例三：定宽加错了层（2026-08 实测）

给主 `<div>` 加 `max-width: 800px` 修「铺满整屏」，结果背景色跟着被夹成 800px 宽的一条，两边露白。**背景色和宽度约束不能挂在同一个元素上**：主容器负责铺满（背景、padding，不限宽），定宽落在内容块上（卡片式主题落在每张卡，无卡片主题落在每个顶层块级元素）。

这个结构早就存在于 CLI 快照路径的产物里并通过了真机验证，是架构改写时丢掉的（同案例二）。**修一个回归时，先看看老版本是怎么做的**——比自己重新设计一遍可靠，那份实现是被真实环境验证过的。

### 同一处的第二个坑：定宽生效了，居中被覆盖了

改完上面那条之后，内容确实定宽了，但全部贴在左边。原因是内联样式的拼接顺序：定宽居中写成 `margin-left: auto; margin-right: auto` 拼在主题样式**前面**，而主题样式里通常有 `margin: 0 0 32px` 这样的简写——**简写在后面就把 auto 覆盖回 0 了**。

所以规则是两条，缺一不可：用 longhand（避免清掉主题的上下间距）**且拼在主题样式之后**（避免被简写覆盖）。

这个错肉眼看代码看不出来（两个属性都在，值也都对），要靠模拟 CSS 层叠算最终生效值才能发现。自检脚本已加：
- 主容器同时出现 `background` 和 `max-width` → FAIL
- 定宽块的实际生效 margin-left/right 不是 `auto` → FAIL（按层叠顺序计算，不是简单查字符串）
