# 主题设计经验教训

> 记录扩展主题在真实生成中翻车的模式、修法和由此形成的规则。新增或修改主题前先读本文。

## 案例一：editor-slate 黑白化（2026-08 实测）

### 现象

用户拿到成品后的原话："配色太单调了，跟 GitHub 给人的感觉不太像，只看到 # 号是蓝色的。"色值普查证实：全文 9 种颜色里强调蓝 `#0969da` 只出现 7 次，且全部落在 h3 的 `#` 前缀上；13 个代码块内部只有底色 + 字色 2 种颜色。整篇实际观感是黑白灰，与主题宣称的"GitHub 视觉语言"严重不符。

### 根因（两层）

**第一层：调色板不等于落点。** 主题文件的「色彩系统」列了强调蓝，但组件规范里蓝色的具体落点只有 h3 前缀、em 和链接——后两者在中文文章里几乎不出现（中文很少用斜体强调，公众号正文没有超链接文化）。生成模型只执行具体指令，不会自己把调色板里的颜色"找地方用掉"。**声明了但没有高频落点的颜色，等于没有。**

**第二层：大面积元素没有内部规范。** 技术文里代码块常占页面一半面积。主题只给了代码块的底色和字色，等于要求生成一块纯色深砖——而 GitHub 的辨识度恰恰来自代码块内的语法高亮（正文越素，彩色代码越跳；只抄"素"的那一半，就只剩素）。

### 修法

1. 新增「语法高亮（必做）」节：GitHub Dark 官方 6 色 token 映射表 + 按语言（YAML/JSON/Bash/Python）的落点建议 + 分寸规则（标点和普通标识符保持默认色，一行上色不超过 3 类，防矫枉过正成彩虹）
2. 提示卡从「可选」改为「遇到就用」，并写明判断标准（"读者跳过会踩坑"）和数量上限（2–4 张）
3. 表格补斑马纹
4. 修复后复测：代码块内 6 种 token 色共 213 处，用户确认观感达标

### 后续（2026-08 全主题实测）

editor-slate 那次修复**只治了一半**。补语法高亮让代码块变彩了，但正文里强调蓝的落点仍然只有 h3 前缀、em、链接——em 和链接在中文技术文里近乎为零。实测产物里正文强调蓝仅 **11 处**，整篇观感达标完全是靠 13 个高亮代码块撑住的。换一篇代码占比低的文章，同样的翻车会再来一次。

真正的修法是给 strong 上强调色（已改）。**这条记在这里是因为它揭示了一个更普遍的错误：修复症状所在的元素（代码块），不等于修复根因（正文落点不足）。**

## 案例二：宽度回归（2026-08 实测）

### 现象

用户在电脑浏览器里对比新旧产物，发现新产物铺满整屏，而早期的 `article.html` / `article-v2.html` 是定宽的——后者更接近公众号在电脑端的真实渲染。

### 根因

CLI 的 V4.0 提示词里「卡片式布局」有一条 `最大宽度: max-width: 800px`。主题被改写成扩展主题格式时**这条被丢掉了**，而 `_common-tech.md` 从来没有接住它。结果：走 CLI 快照路径的产物有定宽，走扩展主题路径的 27 个主题**全部没有**。机械核查确认 27 个主题文件里没有一个提到 `max-width`。

### 教训

**把一份规范改写成另一种格式时，丢失条款是静默的。**改写关注的是"新格式该长什么样"，没有人逐条检查"旧规范里哪些条款没被接住"。而这类丢失不会报错，只会在几个月后由用户在浏览器里发现。

改写规范时的机械做法：把原规范里所有**可验证的技术条款**（数值、属性名）抽成清单，逐条确认在新规范里有对应落点，没有的要么保留要么显式记录为"故意删除"。

### 顺带暴露的检测缺口

这个回归存在了整整一个架构周期，**自检脚本一次都没报过警**——因为脚本只检查"有没有做错"，不检查"有没有漏做"。同批还发现自检脚本对属性截断（`style` 里引号不配对导致整段样式失效）也完全无感。两项均已补进 `wechat-html.md` 的脚本。

## 规则（新主题必须满足）

1. **每个强调色至少有一个高频落点。** 高频元素：h2/h3、strong、列表前缀、引用块边框、表头——每篇文章必然多次出现。低频元素：em、链接、脚注——中文公众号文章里可能整篇为零。强调色只落在低频元素上的主题，产出必然黑白化。
2. **大面积元素必须有内部规范。** 技术向主题的代码块、图文向主题的图注、数据向主题的表格——凡是可能占大版面的元素，只给外壳颜色不够，要写清内部的颜色分布。
3. **调色板里不留死色。** 声明了就要在组件规范里指明落点（哪怕只是"题注、次要信息文字"）；指不出落点的颜色从调色板里删掉。
4. **分寸规则和落点规则成对出现，而且必须互相自洽。** 只写"多上色"会彩虹化，只写"克制"会黑白化。每个主题既要有颜色下限（保底落点），也要有上限（频率/面积预算）。**成对还不够——两条要能同时成立。**2026-08 实测抓到两个反例：ink-wash 写"朱砂频率要低"却把朱砂派给了行内 code（193 处）；ocean-calm 写"一行不超过 2 类上色"却要求"字符串、值、键名全部上色"。字面执行必然违反自己的分寸条款，生成模型只能自行取舍，产物就不可复现了。写完一对规则后，拿本仓库这篇 2.8 万字符、13 代码块的测试文当尺子算一遍：按落点规则这个颜色会出现多少次？超没超过分寸规则给的预算？
5. **黑白是一种设计时要显式声明。** monochrome-mag 无一处彩色是定位本身，文件里写明"无一处彩色"；没写这句的主题出现黑白化就是缺陷。但**声明了无彩色不等于可以没层次**——monochrome-mag 原先只给了两级文字灰，13 个代码块照写就是一块块纯色砖。无彩色主题反而要把灰阶、字重、字号的分工写得更细，因为它没有颜色这个后备手段。
6. **落点分「文字色」和「装饰色」两类，装饰落点不算数。** cyber-neon 的副强调品红有落点（h3 的 `border-left: 3px`），机械扫描不报警，但产物里品红只出现 8 次、全是 3px 细线，在 10 万字符的文档里视觉权重接近零——用户的反馈是"这个蓝色有点单调"。**强调色必须至少有一个高频的文字色落点**（h2/h3 文字、strong、符号前缀），只有边框、细线、小色块的强调色等同于死色。
7. **行内 code 不承担强调色，且装饰必须抗断行。** 技术文里行内 code 密度极高（实测样本 193 处）。把强调色派给它，整页会布满同色斑点，压过真正需要强调的内容（ink-wash 的朱砂、bauhaus-pop 的黄）。更要命的是它跟着正文断行——实心深底 + padding 的装饰在 375px 窄屏下会从中间裂成两截，实测 193 处里 47 处断行。用淡底、小 padding，或只改文字色。已写入 `_common-tech.md`。

## 机械审计方法

**现在有脚本了**，不要再手工扫：

```bash
python3 skills/md2publish-article/scripts/audit-themes.py
```

它对每个主题解析「色彩系统」段，逐色在组件规范里查落点，分三档报告：`DEAD`（零落点）、`LOW`（落点全在 em/链接/脚注这些中文文章里可能整篇为零的元素）、`DECOR`（强调色只当边框细线用，没有文字色落点——规则 6）。2026-08 用它扫出 5 处真缺陷（4 个次级灰零落点 + washi-spring 主强调只当细线），修完全库归零。

写脚本时踩到的坑值得记：**关键词匹配会被规范里的说明文字骗到**。第一版拿关键词在整行里搜，结果「别只挂在 em 上」这句注记让该行被判成 em 落点；把角色标签的判定改成只取冒号前的部分、把落点判定改成先解析元素名之后才干净。改完要做变异测试——把某个主题的落点故意抽掉，确认脚本报警，否则你不知道它是真的没问题还是根本没在查。

以下是脚本背后的判据（脚本覆盖不到的情况仍需人工用它判断）：把「色彩系统」段的色值逐个在正文组件规范里计数，出现 ≤1 次的要人工判断——背景色出现 1 次正常（主容器只写一次），**强调色/辅助色出现 ≤1 次或落在 em/链接上即为风险**。对生成产物跑色值普查（`Counter(re.findall(r'#[0-9a-fA-F]{6}', html))`），强调色计数接近 0 说明落点失效。

2026-08 对当时全部 23 个扩展主题跑过一轮，结果：

- **apple-air**：确认同款风险（唯一强调蓝只落在 em 上），已修复
- arena-charge / aurora-flow / blueprint-grid / mint-breeze：次级灰声明后零落点（死色），已补落点注记
- bauhaus-pop / midnight-study / velvet-stage 等的低计数项经人工判断为误报（落在 h3 边框、引用块边框等高频元素上）
- cyber-neon / retro-phosphor（暗色技术主题）代码块规范色数达标

## 生成方式：脚本做机械层，AI 做判断层

editor-slate v2 的生成方式被证明明显优于纯手写 HTML，固化为推荐做法（`_common-tech.md` 同步收录）：

**脚本负责机械变换**（写一次性转换脚本，不手敲 HTML）：

- HTML 实体转义 → 行首/连续空格转 `&nbsp;` → 换行转 `<br>` → 最后包高亮 `<span>`，顺序固定，从机制上杜绝"高亮标签被转义"和"转义时改坏代码"
- 语法高亮用分语言 tokenizer 产出 `(text, color)` 段再统一渲染，保证 13 个代码块规则完全一致
- 结构性包裹（段落样式、列表悬挂缩进、表格斑马纹）模板化

**AI 负责判断**（脚本做不了的）：

- 哪几段升格为提示卡、哪些保持普通引用（语义判断）
- token 上色的分寸取舍（如 `-d '{...}'` 里的 JSON 是否拆开高亮——不拆，shell 语义上它是一个字符串）
- 主题规范没覆盖到的元素（h1、分隔线、TOML）如何按主题气质补齐

**核对必做**：自检脚本 PASS 之外，把每个 `<pre>` 反解（剥 span → `<br>`→换行 → `&nbsp;`→空格 → 实体还原）与源 Markdown 逐字节 diff，证明高亮没有改坏代码。

这个分工的收益：两次实测（autumn-warm 手写版、editor-slate 脚本版）中，脚本版一次通过全部自检且 13/13 代码块逐字节保真；手写版容易在重复劳动（逐块转义）上出不一致。

## 通用陷阱备忘

- **全局 letter-spacing 污染代码块**：主容器的字距会撑开等宽字符、代码列对不齐。所有 `<pre>`/`<code>`（含行内）显式 `letter-spacing: 0` 复位。已写入 `_common-tech.md`。
- **暗色主题的双模式预览**：微信 App 可能对颜色做映射，cyber-neon / midnight-study / retro-phosphor / velvet-stage 这类暗底主题发布前必须在 App 深色、浅色两种模式下各做一次手机预览。
