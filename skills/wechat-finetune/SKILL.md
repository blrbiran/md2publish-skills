# wechat-finetune：把稿子改成公众号版

## 这个 skill 做什么

接一篇写好的 Markdown，产出**公众号版** `<name>.wechat.md`：标题重拟、内容精简、开篇有钩子、段落适配手机、frontmatter 元数据齐全。原文默认一个字不改——唯一的例外见「事实过时了」那节。

## 为什么需要单独一步

博客读者是**带着问题搜进来的**——他有耐心看背景铺垫，看不懂会往回翻，附录对他有用。公众号读者是**在通勤路上刷到的**——没有搜索意图，前三行不抓人就划走，看不懂不会往回翻、直接退出，附录只是让他觉得"这文章好长"。

同一篇稿子，读者的处境完全不同。所以「写清楚」（`tech-writer`）和「不像 AI 写的」（`tech-writer-deslop`）都做到了，稿子照样可能在公众号里没人看完——那是第三个问题，这个 skill 管这个。

推荐的完整链路：`tech-writer` → `tech-writer-deslop` → **`wechat-finetune`** → `md2publish-article` → `md2publish-draft`。封面走 `md2publish-cover`，与 `md2publish-article` 并行、不进正文。（三期的 `md2publish-visuals` 会把正文配图回写进 Markdown，届时它串在 `md2publish-article` **之前**，不是并行分支。）

## 唯一的判据

每处改动只问一个问题：**读者在手机上划到这里，会不会走？**

会走的原因就三类，对应三种改法：

- **看不懂** → 要么补一句大白话解释，要么整段删掉。判断标准是「这个号的读者知不知道这个前提」，不是「这个概念难不难」。
- **跟他没关系** → 删。原文里对作者重要、对这个号的读者没用的东西（详尽的环境配置、穷举的参数表、写给未来自己看的备忘）是公众号里的死重量。
- **看着累** → 切短。手机屏幕上一段超过 5 行就形成压迫感，长文没有小标题就没有"还有多远"的预期。

删不掉又必须留的难懂内容，是在提示上游的 `tech-writer` 没做完——可以告诉用户，但别在这一步硬改技术表述（见「保真红线」）。

## 保真红线：技术事实只能删，不能改

精炼技术文最大的风险不是删多了，是**把技术改错了**。一个被"顺手改得更通顺"的命令行参数，读者照着敲会失败，而这个错误由公众号署名承担。

所以边界很硬：

- 代码块、命令、参数名、配置项、版本号、数字、报错原文——**原样搬运**。整块删掉可以，块内一个字符都不动。
- 不引入原文没有的技术断言。拿不准某个说法对不对，就删掉，不要"改成正确的"——你没有原文作者的上下文。
- 改写只发生在**叙述性文字**上：开场白、过渡句、解释性段落、小标题。

`scripts/verify.py` 会把产物里的每个代码块拿回原文逐字节比对，改动过就报 FAIL。这不是不信任你，是这类错误肉眼极难发现。

## 事实过时了：唯一允许改技术内容的情况

上面那条红线防的是「不懂装懂改坏」，不防「事实真的变了」。技术类公众号有时效性——模型 ID、SDK 版本、端点地址、定价，几周就能作废。作者要求更新这类内容时照做，但按下面的顺序。

**先找真值源，再动手。** 本机常常就有：源码仓库（`sourceget find <包名>` 能定位）、包自带的数据文件、官方文档。有真值源就逐条核对，别凭记忆——**你的知识截止日期几乎总是早于用户手上的现实**，用户知道厂商上周发了什么，你不知道。

核实结果分三类：

| 情况 | 怎么办 |
|---|---|
| 核实通过 | 直接改，在报账里写清依据（版本号 + 核对日期） |
| 核实**不通过**（新值查不到） | 停下来，摆出你查到的当前值。用户坚持就照改，但要在文中标明这条的代价 |
| 核不了（没有真值源） | 说清「我核不了，依据是你的确认」，然后照改 |

第二类最容易出事，也最有价值。实测过一次：用户给的两个模型 ID 在真实计价表里查不到，直接填进配置文件会让读者第一条命令就失败。停下来问比"听话"重要。用户确认上游确实已发布之后，正确做法不是沉默照改，而是**改了并在文中补一句边界**（"这个还没进计价表，能调通但花费显示 0"）——读者照抄就不会踩坑。

**改动落在原文，不是只落在公众号版。** 公众号版是原文的派生物，只改派生物，下次基于原文再生成就退回旧值；而且 `verify.py` 逐字节比对代码块，两边不一致直接 FAIL。所以顺序是**先改原文，再生成公众号版**。

**顺手发现的硬伤也归这一类。** 逐段精炼是全流程中最可能撞见原文错误的时刻（实测撞见过一处"冒号"该是"斜杠"、一条已经不成立的协议断言）。发现了就报告，别假装没看见——但同样先核实再改。

## 怎么问用户

这个 skill 有三处必须让用户拍板：画像、本文目的、标题。**问法比问什么更容易出错。**

**开放性问题要留一个「我自己填」的槽位。** `AskUserQuestion` 最多 4 个选项，把 4 个占满，用户就只能走「其他」——而那条路径会跳出问答流程变成聊天，等于白问一轮。标题、署名这类答案空间无限的字段尤其明显：用户想要的往往是"我给你个方向你重拟"，不是从你预设的四个里挑。所以这类问题**最多给 3 个候选，第 4 个明确留成「我自己写 / 我给个方向」**。

实测过一次失败：连问三轮、每轮 4 个满槽，用户三轮全被迫走「其他」，每次都打断流程。问题不在轮次多，在没给他地方说话。

**用户连续改用聊天回答时，后面就用散文提问。** 那是偏好信号，不是没看懂。

**能推断的先推断，让用户改而不是填。** 画像和目的都能从原文读出八成，给草案让用户否决，比给空白让他写快得多。

## 执行流程

### 步骤 1：拿到输入，载入画像

读用户给的 `.md`。**开工前先说一句产物路径**：默认写同目录的 `<name>.wechat.md`，原文件不动。用户没问也要说——他们往往不知道原文会不会被覆盖，主动说清省掉一轮来回。用户指定了路径就用他们给的。

然后找画像文件 `./.md2publish/audience-profile.md`（当前工作目录下）：

- **存在** → 读它，跳到步骤 2。
- **不存在** → 先读完原文，**推断**出一份画像草案（这个号大概是做什么的、读者是谁、语气偏好），用 `AskUserQuestion` 给用户确认或修改，然后按 `references/audience-profile-template.md` 的格式存盘。

推断优先、再让用户确认，比直接甩问题给用户强——用户改选项比填空快得多。

### 步骤 2：确认本文目的

同一个号的不同文章目的不同：涨粉的、树立专业形象的、给老读者交付干货的、推产品的。目的直接决定标题往哪个方向拟、哪些内容该留。

从原文推断出 2–3 个可能的目的，用 `AskUserQuestion` 让用户选。用户自己说了就直接用。画像和目的是同一组前提，合并成一次 `AskUserQuestion` 问完（一次调用可以带多个问题），别拆成两轮。

### 步骤 2.5：能核实的先核实

**只查原文自己给了验证方法的地方**，不是全文事实核查。技术文里常见的可核实项：文中写出的查询命令、文件路径 + 函数名、包名和版本号、API 端点。这些跑一次或 grep 一次就有答案。

值得花这几分钟，是因为**精炼过程会把这些内容原样搬进公众号版，错的也一起搬**，而公众号版是要署名发出去的。实测收益：跑一次文章自己给出的那条查询命令，就发现文中两个模型 ID 已经不在计价表里；grep 一次源码目录，发现一条协议支持的断言已经不成立——两处都会让读者照抄失败。

本机有对应源码仓库时优先用它（`sourceget find <包名>`）。核出问题按上面「事实过时了」那节处理：先报告，再决定改不改。核不动就跳过，别硬编——这一步是加分项，不是准入门槛。

### 步骤 3：精炼正文（自动做完，不逐条问）

按「唯一的判据」逐段处理：

- **删**：难懂且非核心的、与本号读者无关的、纯备忘性质的。记账（步骤 6 要报）。
- **开篇钩子**：技术文常见的开头是「背景介绍 + 本文将要讲什么」，这是博客写法。换成直击痛点或制造张力的开场——读者的问题、一个反常识的结论、一个具体的翻车现场。原文如果已经有好开头就别动。
- **段落切短**：超过 5 行的段落找语义断点拆开；超过 3 个逻辑层次的长文补小标题。
- **结尾引导**：按画像里的模板加。画像里没配就不加。

原文的 H1 标题提到 frontmatter 去，正文里不再保留——公众号的标题由草稿元数据承载，正文里再出现一次是重复（下游 `md2publish-article` 也按这条规则渲染）。

### 步骤 4：拟标题（这一步必须让用户选）

标题是全篇打开率的单点决定因素，也是最主观的东西，不该由 skill 替用户拍板。

出 **3 个走不同路子的候选**，每个标好字符数（微信硬限制 32 字符），**第 4 个选项留成「我自己写 / 我给个方向」**——理由见「怎么问用户」。四种路子和好坏对照见 [references/title-patterns.md](references/title-patterns.md)——务必读它再拟，那里记了什么样的标题是"标题党"（承诺了正文给不了的东西）而什么样的是"有钩子"。

**用户自己给标题时，先数字符。** 他们不会数，而超限的标题要到建草稿那一步才被拒，来回一轮很浪费。超了就优先做**不改字的压缩**：去掉中英文之间的空格、换更短的标点。实测一句 36 字符的标题，只去掉 4 个空格就回到 32，用户一个字没改。压不下来再提议删字，并说清删的是哪几个字、挪到哪里（通常挪进 `digest`）。

用户选中或自己写的路子记回画像的「标题偏好」，连同他**否决过的方向和说法**一起记——否决信息比选中信息更能防止下次重犯。

### 步骤 5：组装 frontmatter

```yaml
---
title: <用户选定的标题>      # ≤32 字符
author: <画像里的署名>        # ≤16 字符
digest: <摘要>               # ≤128 字符，公众号列表页的那行小字
---
```

摘要不是标题的复述，是**给已经被标题吸引、正在犹豫点不点开的人看的**——补充标题没说完的信息，或者给一个具体的收益承诺。

画像里没有 author 就问用户一次，然后记进画像。

### 步骤 6：写出产物 + 报账

写 `<name>.wechat.md`（同目录）。路径已存在文件时先问用户是否覆盖。

然后给用户一份改动清单：

```
标题：<原> → <新>
删减：N 处，共 X 字符（原文 Y 字符，保留 Z%）
  - 「XX 环境配置」整节 —— 与本号读者无关
  - 第 3 段末两句 —— 依赖未交代的前提，读者会卡住
新增：开篇钩子（3 行）、小标题 4 个、结尾引导
```

删减超过 30% 时明确提示用户复核——精简过头和精简不足一样是问题，而只有用户知道哪些内容是他舍不得的。

### 步骤 7：自检（不可跳过）

```bash
python3 scripts/verify.py <原文.md> <产物.wechat.md>
```

检查：代码块逐字节保真、frontmatter 三个字段齐全且不超限、正文无残留 H1、删减比例统计。任何 FAIL 修完重跑到 PASS 才交付。

改过原文（见「事实过时了」）的话，两个文件都要重跑——代码块是拿原文当基准比的，只改一边必然 FAIL。

**两条 WARN 的读法**，知道了就不用每次追：

- **「行内 code 有 N 处在原文中不存在」**：脚本先剥掉代码块，再从散文里收集行内 code。所以一个只在代码块里出现过的标识符，你在散文里第一次提到它就会被报。看一眼是不是这种情况，是就放过。
- **「删减超过 30%」**：不是错误，是让作者确认。技术长文在公众号里删掉三成很常见，作者说「删多了没问题」就继续，别自己往回加。

### 步骤 8：交接

报告产物路径、改动清单、自检结果，然后问下一步：转 HTML 走 `md2publish-article`，要封面走 `md2publish-cover`；要正文配图 / 信息图 / 示意图，如实说 `md2publish-visuals` / `md2publish-diagram` **三期才建、现在没有**，别拿封面流程凑合。不要未经询问就往下走。

## 画像文件

`./.md2publish/audience-profile.md`，格式见 [references/audience-profile-template.md](references/audience-profile-template.md)。它是**用户的资产不是缓存**——用户手改过的内容不要覆盖，只在用户确认后追加或修改对应字段。

一个仓库/工作目录一份画像。用户同时运营多个号时，让用户说清这次用哪个定位，或者建议他们分目录。
